# gmgn radio 产品与技术设计

日期：2026-07-28  
状态：已确认方向，待实施

## 1. 产品定义

gmgn radio 是一款 macOS 原生 AI 电台。它长期存在于桌面，以一颗带 VFX 光晕的呼吸球作为默认身体。球体里的 DJ 能实时听懂用户说话，理解当下情绪与场景，自主决定何时回应、何时保持安静、播放什么音乐，以及怎样完成歌曲之间的串场。

产品默认没有传统播放器界面。播放、聊天、选歌和调整氛围都通过自然语音完成；设置、音乐库管理和人格编辑等低频操作才使用窗口。

第一版招牌场景是“深夜个人电台”：用户独处、工作或放松时，DJ 通过实时对话、连续选歌、克制串场和音画联动，形成一段只属于当晚的节目。

## 2. 核心原则

1. **DJ 有自主性。** 用户提供偏好和边界，DJ 自己决定具体行为。设置项表达倾向，不把 DJ 变成逐项执行指令的遥控器。
2. **语音是主入口。** 用户不需要判断自己正在聊天、控制播放器还是表达情绪，模型统一理解。
3. **安静也是能力。** DJ 可以主动说话，也必须知道什么时候不该说话。
4. **界面退到背景。** 日常只保留呼吸球与 GFX；歌名、按钮和状态只在需要时出现。
5. **音画共用时间线。** DJ 语音、音乐、压低音乐、节拍分析和视觉表现必须同步。
6. **先做 macOS 长板。** 首版只支持 Apple Silicon 和较新的 macOS，不为旧系统、Intel 或 Windows 降低表现力。
7. **隐私状态必须可感知。** 用户随时能看出麦克风是否在监听，并能用一句话关闭监听。

## 3. 第一版体验

### 3.1 首次启动

首次启动只完成必要配置：

1. 解释并申请麦克风权限。
2. 连接一个流媒体音乐账号。
3. 选择一个或多个本地音乐目录。
4. 使用默认 DJ，或用一句提示词调整它的性格。

完成后传统窗口关闭，桌面右下角留下低亮度呼吸球。人格、声音、主动程度、音乐偏好和隐私设置可以稍后调整。

### 3.2 麦克风模式

麦克风有三个明确状态：

- **待机：** 只在本机识别唤醒词，不上传环境声音。
- **单轮对话：** 唤醒后进行一轮实时交流，结束后自动回到待机。
- **陪伴时段：** 持续聆听，呼吸球始终显示明确的监听状态。用户说“你先别听了”即可退出。

同时提供全局快捷键，方便用户不说唤醒词直接开口。

### 3.3 深夜节目流程

用户说：“今天有点累，想听安静一点的，但别太伤感。”

DJ 用一句自然回应确认氛围，同时搜索流媒体和本地音乐库，尽快开始第一首歌。它不先展示歌单，也不要求用户选择风格。

播放过程中，用户可以随时说：

- “这首有点太冷。”
- “沿着刚才那首继续。”
- “少说话，陪我工作。”
- “歌小一点，我想跟你聊聊。”
- “这首不错，记住这种感觉。”

DJ 根据反馈调整后续队列，保留已经建立的整体气氛。歌曲切换时，它可以自主决定是否插入简短串场。用户说“晚安”后，音乐缓慢淡出，DJ 用一句话结束当晚节目，并在本地记录本次偏好。

## 4. DJ 自主性

DJ 的决策输入包括：

- 用户当前说的话；
- 用户允许使用的语音情绪特征；
- 当前时间、播放历史和会话上下文；
- 用户的长期音乐偏好；
- 当前歌曲、队列和连续跳过等行为；
- 用户设置的主动程度与禁区。

DJ 每次决策可以选择：

- 回应用户；
- 保持安静；
- 搜索或播放歌曲；
- 修改后续队列；
- 调整音乐音量；
- 在转场时串场；
- 邀请用户进入或退出沉浸模式；
- 记录一个偏好，或忽略一次偶然行为。

设置栏只调整倾向，例如“更健谈 / 更安静”“熟悉歌曲 / 探索新歌”“温柔陪伴 / 有观点的 DJ”。具体时机仍由 DJ 决定。

用户提示词定义 DJ 的稳定人格。系统将自由文本整理成结构化配置，并与基础安全边界、长期记忆和当前会话分开保存，避免人格随对话漂移。

## 5. 呼吸球与 GFX

默认身体是一颗带多层 VFX 光晕的呼吸球。它借鉴实时语音产品的清晰状态隐喻，但使用 gmgn radio 自己的材质、色彩、粒子和动作语言。

状态表现：

- **待机：** 缓慢呼吸、低亮度、低刷新率。
- **唤醒：** 光晕聚拢，球体产生快速但柔和的响应。
- **聆听：** 外圈根据用户声音形成波纹，清楚表示麦克风正在工作。
- **理解：** 内部光流旋转、折叠和重组，不显示加载图标。
- **说话：** 球体由 DJ 的真实音素、响度和语速驱动。
- **播放：** 颜色、粒子、形变和光晕响应节拍、频谱与歌曲结构。
- **隐私关闭：** 光晕收缩，呈现清晰、克制的断开状态。

球体支持自由拖动和边缘吸附，记住每台显示器的位置，并避开 Dock、菜单栏和系统安全区域。鼠标靠近时才显示歌名、收藏、跳过、唤醒和隐藏等少量控件。

进入沉浸模式时，球体向外溶解并成为全屏 GFX 的视觉核心；退出时重新凝聚回桌面。GFX 可以使用当前歌曲的节拍、频谱、段落、DJ 状态与当晚情绪轨迹共同驱动。

## 6. 原生技术架构

### 6.1 技术选型

- **Swift + AppKit：** 应用生命周期、透明窗口、悬浮层级、菜单栏、Spaces、全局快捷键和系统媒体集成。
- **SwiftUI：** 设置、音乐库、人格编辑器、权限说明和诊断界面。
- **Metal + MetalKit：** 呼吸球、粒子、着色器、全屏 GFX 与高刷新率渲染。
- **AVAudioEngine + Core Audio：** 音乐播放、DJ 语音、混音、压低音乐、音频分析和输出设备管理。
- **Swift Concurrency：** DJ 状态机、实时会话、搜索、队列与模型调用。
- **SQLite：** 本地音乐索引、节目历史、用户偏好、人格配置和长期记忆。
- **LiveKit Swift SDK + LiveKit Agents：** 实时音频传输、打断、会话管理和 Agent 运行时。
- **OpenAI 兼容模型接口：** 通过服务端配置切换模型和端点，不把具体供应商写进客户端。
- **ElevenLabs TTS：** 提供 DJ 的定制声线；DJ 自主性、工具和记忆仍由 gmgn radio 管理。

Rust、React、Tauri、TanStack 和 shadcn 不进入首版主程序。将来出现明确的本地推理、复杂 DSP 或跨客户端共享需求时，再抽取边界清楚的 Rust 模块。

### 6.3 数据流

```text
本地唤醒词
    ↓
开启实时麦克风会话
    ↓
语音内容 + 可选情绪特征 + 当前播放上下文
    ↓
LiveKit Agents 调用 OpenAI 兼容模型
    ↓
DJCore 验证回应与节目决策
    ├── VoicePlayer 播放 DJ 语音
    ├── MusicSources 搜索歌曲
    ├── ProgramPlanner 更新动态队列
    └── VisualEngine 更新角色状态

MusicPlayer 输出音频
    ↓
AudioAnalysis 提取响度、频谱、节拍和段落
    ↓
VisualEngine 按音频时间戳渲染呼吸球与 GFX
```

音乐和 DJ 语音使用独立通道。DJ 开口时，音乐自动平滑压低；结束后按歌曲状态恢复。视觉系统读取带时间戳的分析结果，避免经过界面状态转发。

LiveKit 只负责实时会话与音频传输。模型使用 OpenAI 兼容协议，ElevenLabs 只负责 DJ 声线。播放队列、工具执行、用户偏好、长期记忆和隐私状态以 macOS 客户端为权威，避免外部 Agent 平台控制核心产品行为。

## 7. 音乐来源

第一版支持：

1. 一个流媒体账号；
2. 用户本地音乐目录。

两者通过统一的 `MusicSource` 协议提供搜索、播放能力、元数据、封面、收藏状态和可用性。DJ 可以混合使用两个来源，并记录用户更偏好哪一类结果。

实时生成音乐、社交电台、多人房间和音乐市场不进入第一版。

## 8. 异常处理

异常默认由 DJ 和呼吸球共同处理，尽量避免弹窗打断节目：

- **歌曲不可用：** 保留当前气氛，自动更换候选歌曲；必要时由 DJ 简短说明。
- **网络波动：** 优先继续已缓冲或本地音乐，球体显示克制的连接状态。
- **实时模型中断：** 音乐继续播放，DJ 暂时保持安静；恢复后不补说过时内容。
- **麦克风权限缺失：** 球体仍可播放音乐，点击后打开明确的权限修复入口。
- **音频设备切换：** 暂停新的 DJ 发言，完成输出重建后继续节目。
- **Metal 渲染故障：** 保留低复杂度的基础球体，音乐与语音不能因此中断。
- **流媒体登录失效：** 继续使用本地音乐，并在用户主动靠近球体时显示修复入口。

技术错误会写入本地诊断日志，但不会把原始麦克风音频或完整对话默认写入日志。

## 9. 隐私

- 唤醒词默认在本机识别。
- 陪伴时段必须始终有持续可见的监听状态。
- 原始麦克风音频默认不长期保存。
- 语音情绪分析可以单独关闭。
- 屏幕和系统音频感知不进入首个版本；后续只能通过明确授权按场景启用。
- 长期记忆必须可以查看、编辑和清空。
- 用户说“别记住这个”时，本次内容不能进入长期记忆。

## 10. 验证标准

首个可用版本至少达到：

- 唤醒后 100 毫秒内出现明确视觉反馈；
- 网络正常时，DJ 首段语音的感知等待尽量控制在 800 毫秒以内；
- 音乐来源可用时，用户表达场景后 5 秒内开始播放；
- 音频分析到视觉呈现的目标偏差不超过 30 毫秒；
- 普通屏幕持续稳定 60 帧，高刷新率屏幕按能力提升；
- 待机时主动降低刷新率和音频分析负载；
- DJ 说话时压低音乐平滑、无爆音、无明显音量跳变；
- 切换耳机、外接声卡或显示器后能够恢复；
- 网络、模型或流媒体故障时，正在播放的音乐尽量不中断。

测试层次：

1. DJ 状态机、偏好和记忆策略的单元测试；
2. 音频图、压低音乐和设备切换的离线与真机测试；
3. Metal 场景的固定输入帧回归测试；
4. 权限、唤醒、睡眠恢复和多显示器的端到端测试；
5. 深夜连续运行数小时的功耗、内存和稳定性测试；
6. 真实用户盲测，重点观察 DJ 是否说得太多、选歌是否连续、视觉是否打扰工作。

## 11. 第一阶段不做

- Windows、Linux、Intel Mac 和旧系统兼容；
- 多位预设 DJ；
- 桌宠市场和皮肤市场；
- 实时生成音乐；
- 多人房间、关注、分享和社区；
- 屏幕内容理解；
- 复杂传统播放器页面；
- 面向所有音乐服务的统一兼容层。

## 12. 建议实施顺序

1. **视觉原型：** 原生透明窗口、呼吸球状态、Metal 音频响应和全屏转场。
2. **音频原型：** 本地音乐播放、DJ 独立语音通道、压低音乐与设备切换。
3. **语音原型：** 本地唤醒词、单轮实时对话和陪伴时段。
4. **DJ 闭环：** 场景理解、动态队列、自主串场、偏好与会话记忆。
5. **音乐来源：** 本地音乐库完善，并接入首个流媒体服务。
6. **控制中心：** 权限、人格、主动程度、音乐偏好、记忆和诊断。
7. **长时间打磨：** 功耗、延迟、多显示器、睡眠恢复、弱网与连续节目质量。

第一阶段完成的判断标准，是用户可以在深夜只说一句自然语言，随后获得一段持续、连贯、具有 DJ 存在感且不打扰的个人节目。
