# Living Space：从一名居民到 AI BnB 的迭代计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal：**让用户拥有一个能装修、能观察、能留下经历的 Agent 生活空间，逐步开放内容分享、空间访问、创作者经营和商业合作。

**Architecture：**先复用 macOS 客户端、Marble 环境、独立实时物件与 WorldRuntime；让文字和语音共用同一名居民、同一个 Agent 会话及空间工具。空间内容、个人存档、模型账户分开，随后增加可移植空间包、访问实例和创作者市场。

**Tech Stack：**现有 Swift、AppKit、SwiftUI、Metal、WorldRuntime、Marble/SPZ、GLB、VRM/PMX、VRMA/VMD、命令行 Agent 适配器；后续服务端和引擎选择留到具体能力验证时决定。

日期：2026-09-05。初版规划的代码基线：`4cb6c32`，当时只做规划。后续按用户指令逐项实施，最新实现与测试结果见 `evidence/2026-09-05-living-resident-loop.md`；下方“当前真实起点”保留初版审计状态，不能用作最新验收结论。

## 一、这份计划遵循什么

本计划以用户在最初研究案之后的讨论和选择为准。早期研究案中的家园经营、小镇、多人、副本规模、团队和周期估计，不作为本计划的执行约束。过去的工程文档继续提供技术证据；产品范围冲突时采用本计划。

产品存在的意义：用户为一个 Agent 创造一个地方。看到它在这里生活、使用自己摆放的东西、留下经历，就能产生陪伴和归属感。用户可以随时参与，也可以安心做自己的事。

已明确的边界：

- 先一名 Agent；首期不做多角色编排。
- 以观察为主，Live Cam 是常驻入口。附身操作以后再加，不阻塞首期。
- 空间可以是飞船、木屋或其他地方。模板帮助用户理解能做什么，不限制用户的想象。
- 提供三个成型角色选择；性格以用户可编辑提示词和模板表达，不先建设复杂人格数值系统。
- 思考模型、语音识别、语音合成分开配置。保留 Codex、dsh、Claude Code、WorkBuddy、Qoder、pi 的接入方向。
- 让用户看得懂、Agent 玩得动、普通电脑跑得起。素材生成成本和分享速度优先于高模画质。
- 先分享日常内容，再开放可进入的房间，再验证收费租用。摊主经营空间，访客为自己的 Agent 提供模型额度。
- 原材料、动作、外观、工具和模型额度可以成为商品。索引、推广、订阅连接和商业体验合作分阶段验证。
- 首期只保留执行活动、保存结果和控制调用所需的约束，不加入战斗数值、复杂经济、好感等级、强制种田或大型多人系统。

## 三、总路线

每阶段交付一个可以玩的版本。阶段验收通过后再向后扩展；阶段编号表示依赖关系，不要求所有远期设想同时上线。

| 阶段 | 用户拿到什么 | 核心工作 | 放行条件 |
| --- | --- | --- | --- |
| 0：守住现有版本 | 能持续进入、观察、聊天、切换播放器的生活舱 | 固定回归、错误状态、低负载与安装流程 | 修新功能不会让旧入口、动作、视角再次失效 |
| 1：让居民听懂并做到 | 对它说“去放首歌”，它能走过去执行并回应 | 统一会话、语音转写、环境上下文、动作工具、TTS | 同一个会话串通输入、行动、结果、回答 |
| 2：让它自己生活 | 用户不操作时，它会找事做；回来能看到经历 | 少量实用物件、自主活动、打断、预算和事实日志 | 安静观察半小时仍有合理行为，能随时叫停 |
| 3：让用户搭建 | 选模板、选角色、摆物件、写性格、保存自己的空间 | 最小装修工具、素材包、生成导入、许可信息 | 新用户能做出一个明显不同且角色可用的空间 |
| 4：先分享日常 | 分享照片、短录像和空间名片 | 本地导出、隐私预览、内容展示与创作反馈 | 分享足够快，不要求对方安装应用或进入房间 |
| 5：扩展空间能力 | 电视能播内容，摄影棚能演片段，门能连接另一个地方 | 场景接口、能力适配、跨空间切换、可选高光 | 新物件能复用接口，无须复制一套应用逻辑 |
| 6：开放访问和短住 | 带自己的 Agent 去别人搭建的空间，回来保留经历 | 空间发布、实例隔离、访问权限、版本与可移植存档 | 别人的内容不能修改我的账户、文件或私人记忆 |
| 7：开放创作者经营 | 摆摊、租用、出售积木包和明确标注的推广 | 索引、订单、授权、燃料归属、用量和结算 | 至少完成真实创作者—访客服务闭环与退款演练 |
| 8：合作体验与扩展世界 | IP 空间、品牌物件、订阅内容、主题体验和游戏入口 | 商业合作、体验包、专用游戏规则和按需托管 | 有持续创作和使用证据，再投入大型体验 |

节奏建议：按一周整理一个可试玩增量，但不承诺一周完成一个阶段。阶段 1 完成后，用实际开发速度和成本估算后续；商业化与 IP 合作依赖外部参与，不写固定上线日期。

## 四、阶段 0：把每次修好的东西留下来

这是伴随所有阶段的回归工作，不单独启动一轮大重构。

固定验收路径：启动 → Live Cam → 空间 → 播放器 → 设置四分区 → 返回空间 → 发消息 → 切动作 → 退出后再进。加入 WASD、滚轮、拖动和双击复位。

每个发布候选记录构建版本、空间包版本、已跑测试和未测事项。聊天框显示真实的处理中、完成、失败、取消状态；连接提示不能沿用旧麦克风状态。构建成功、后台进程存在、用户实际体验通过分别记录。

性能先测用户当前机器：冷启动、空间载入、前台观察、后台 Live Cam 各自的帧率、内存、CPU/GPU 占用。记录机器和测试条件后再定预算，不能把一台高配机器的结果当最低配置。隐藏窗口降低渲染频率；不因日常活动持续调用大模型。

已发现长期驻留风险：当前世界按高频时钟推进，时间事件持续追加到内存数组。先确认增长曲线，区分可丢弃的时钟细节与需要留下的活动结果，避免把每帧记录永久保存。

安装仅到 `/Applications/gmgn radio.app`，替换可恢复。凭据不再访问钥匙串，不自动迁移旧项目；本地存储需限制权限且不进入日志、导出或空间包。具体存储不等于加密保护，发布前需单独说明和检查。

## 五、阶段 1：一个入口、一名居民、一个会话

输入链路统一为：

`文字输入／语音转写 → 同一会话 + 当前空间信息 → Agent 请求动作 → 应用执行 → 返回结果 → 文字显示／TTS／表情动作`

按以下顺序交付：

1. **先打通一种提供方。** 用用户选定且当前可用的一种完成真实端到端验证，优先尝试现有 Codex 接入；失败时明确原因，不静默切到另一个模型。六种适配器保留并逐一补验收。
2. **先让它知道空间里有什么。** 送入当前空间、人物位置、可用物件、活动、正在执行的事情和最近结果。使用结构化描述；截图或视觉理解按需补充，不让它凭场景名称猜设施。
3. **再让它实际调用动作。** 第一条验收命令是“去点唱机放首歌”。工具返回已接受、执行中、成功或失败；聊天只把真实成功说成完成。活动编号、设备是否存在、实际播放条件由现有运行时确认。
4. **接语音输入。** 语音先转文字，再进入同一个会话；保留文字纠错。断句、取消和新消息打断不能制造重复行动。
5. **输出统一。** 同一份回答可选文字、语音或二者。TTS 切换不改变思考模型，会话失败不能残留“正在说话”动画。
6. **提供用户可编辑提示词。** 人格描述负责风格与倾向，当前物件和可用工具由应用提供。现有 DJ 编排提示词不能直接算作聊天人格已接通。明确提示词不会给尚未实现的道具创造能力。

当前 dsh 适配使用内存中的最近六条消息，尚无与其他提供方等价的原生续聊；需要明确其恢复方式。初版 TTS 使用系统朗读。用户后续确认的实施顺序是：先完成百炼独立 TTS 和音色切换，再增加豆包、Fish Audio、ElevenLabs，以及支持服务地址、鉴权、模型与音色配置的高级自定义服务。各项分别验收，不能将接口抽象写成已支持全部服务；详细步骤见第一阶段实施计划的任务 6、6A。

空间聊天默认收起在右下角固定控制条内，点击聊天按钮后展开文字和语音输入，随时可收起；不让输入框常驻遮挡生活空间。

验收脚本：连续要求“这里有什么”“去放首歌”“先停下”“刚才做了什么”。实际动作、界面状态和回答一致。关闭 TTS 后可正常文字交互；模型失败、语音失败和无可播歌曲分别可见且可重试。

六提供方验收表必须逐行填写：发现程序、发文字、连续会话、取消、世界只读工具、世界写入工具、错误回传、语音输入共用会话。某项未实现就明确显示，不用一个“已连接”涵盖全部能力。

## 六、阶段 2：有日常可做，用户可以不管它

先在现有飞船舱内补齐五类行为，不换新房间：听音乐、坐下休息、操作灯光、喝咖啡、看窗外。跳舞沿用已有动作；具体角色不兼容的动作不列入它可选择的活动。咖啡暂不做原料经济，先完成设备状态、杯子表现和动作反馈。

自主活动复用当前调度与执行器：

- 用户指令优先，聊天可中断活动；手动动作不会立刻被自主活动抢走。
- 常规活动用轻量选择、冷却和持续时间控制，重要变化再请求模型。
- 同一活动失败后退出并说明原因，不无限重试、不连续空转。
- 用户可以暂停自主活动、控制主动说话频率、设置模型调用预算。
- 桌面观察允许一段时间安静待着，不把频繁走动和说话当成“活着”。

经历先做事实日志：何时去了哪里、操作了什么、结果怎样、用户参与了什么。Agent 只能据这些记录回顾，不先建设复杂关系数值和长期人格反思系统。

应用关闭时明确显示“世界暂停”或按已声明规则结算。没有服务器运行的情况下，不声称 Agent 离线一直思考和活动。以后开通托管，再升级为持续运行。

验收：连续观察 30 分钟，有多种合理活动且没有卡死；用户中断后不继续旧请求；重进空间位置与物件状态合理，能回顾真实经历；能查到模型调用次数和失败次数。完成这一阶段即可邀请少量用户试用；阶段 4 的本地照片导出可以提前交付。

## 七、阶段 3：用户自己的空间和积木

首个编辑器只做添加、移动、旋转、删除、撤销、保存。暂缓复杂地形编辑、多人协同和大型资产商店。

物件分清两层：

- **外观素材：**GLB 网格、贴图、尺寸与碰撞。可以是咖啡机，也可以是月光大剑。
- **可用能力：**可做的活动、交互位置、动作适配、设备状态和应用接口。普通模型导入后默认是装饰；只有绑定已支持能力才可交互。

每件物品有稳定编号、来源、版本、依赖和许可说明。移动物件后，模型位置、碰撞、操作点、Agent 感知同时变化；删除当前正在使用的物件应中止活动。导航先采用重新校验可达性和已有路径点，确有需要时才扩展动态导航。

提供三个起步空间模板，例如飞船生活舱、温暖木屋和小型工作室；先做深当前飞船，再制作另外两个，避免维护三份未完成样片。用户可从模板改造、导入素材，也可通过生成工具创建新的环境底稿。生成前显示用量提示，生成后执行比例、碰撞、导航和资源预算检查。

提供三个授权条件清晰的成型 VRM；当前 2B 研发演示素材不能自动成为商用赠送资产。角色提示词、模型选择与空间模板分开，换房间不重置人格。

验收：用户不用改代码即可摆放三件独立物件，其中至少两件可用；Agent 能发现变化并走到新位置操作；撤销和重进后布局一致；资产缺失与不兼容可见。

## 八、阶段 4：分享日常，先验证内容吸引力

先交付截图、短录像和简单日记卡片的本地导出，再做公开内容流。画面展示同一空间中真实发生的动作。发布前可以选择片段、隐藏聊天文字、确认人物声音和素材可分享范围。

空间名片包含作者、预览、模板来源和可做的事情；此时“看看空间”可以只看内容，不伪装成已经可以进入。记录关注、收藏、想访问和想获得哪些物件的意愿。

图像生成或视频生成作为可选纪念功能；由用户确认消耗额度，失败可放弃，不能拖住实时画面。生成视频与真实录像分开标识。

验收：至少找几位未参与开发的人试用导出和观看流程，观察他们能否看懂“这是一个会生活的角色”以及是否愿意分享。用户先选内容再发布；私人会话、账户、文件路径和密钥不能随内容流出。

## 九、阶段 5：场景接口让物件越来越有用

将点唱机专用实现整理成可复用能力接口，再按需求加入：

| 物件／空间 | 对接能力 | 首个可验收版本 |
| --- | --- | --- |
| 点唱机 | 现有音乐播放、切歌、音量、镜头 | 走到设备、动作开始、实际播放、结束镜头；精细插唱片动作独立迭代 |
| 电视机 | 授权视频、订阅内容或 AI 节目流 | 播放、暂停、屏幕画面、Agent 观看活动；不烘焙进 SPZ |
| 摄影棚 | 角色动作、对白、镜头和录制 | 演一段短场景，可打断、可导出，不预设完整电影生产线 |
| 门／传送入口 | 另一空间包与入口位置 | 带同一居民过去，再返回；历史与账户继续属于用户 |
| 游戏入口 | 独立二维或三维小游戏适配器 | 先一个授权简单小游戏，说明控制主体、暂停和返回规则 |

每个接口声明能做什么、所需权限、费用归属和完成信号。创作者内容无权直接执行任意本地命令，也不能读取用户的模型账户。先开放内置能力和有限参数，后续再考虑带审核与隔离的扩展代码。

Bevy、Godot 或其他引擎暂不作迁移决定。到“通用 GLB 交互物件”和“外部小游戏”两个节点，各做一次小样：加载同一资产、触发同一活动、保存状态、测目标机器开销。现有客户端能满足就继续复用；不能满足时只评估需要替换的部分。

## 十、阶段 6：可以打卡，也可以让 Agent 住一晚

第一版可进入房间采用“下载经校验的空间包，创建自己的访问实例”。原作者的房间不被访客覆盖，访客之间默认互不影响；暂不需要所有人同时在线。

分开保存：空间模板、作者发布版本、访客自己的访问实例、访客带回的经历。更新空间时保留旧访问版本，避免参观到一半家具和规则改变。空间退出后恢复自己的家；带回经历与获得某个物件的使用权分开处理。

所有权先从存档导出、导入、备份、迁移做起。后续增加个人托管空间和可选自托管，明确模型账户、存储、费用和停机影响；首期不要求用户会运维服务器。

建立发布前资源检查、访问权限、违规举报与撤下流程。包内文本视为内容数据，不得覆盖用户或应用的操作权限。私有聊天、联系人、文件和其他空间记忆默认不提供给作者。

验收：两位用户分别访问同一空间，状态隔离；更新不破坏在访实例；返回后保留正确经历；撤回分享后阻止新访问。离线已下载内容能否撤回需如实说明，不承诺远程删除用户已有副本。

## 十一、阶段 7：从跳蚤市场逐步形成经营

先让少量创作者真实发布、接待和定价，再决定平台费率，不把“大量小 B 必然涌入”当成既成事实。

### 费用和燃料

- 作者承担创作素材、制作工具、生成和自己的后台运营成本。
- 访客默认使用自己的模型账户或自己购买的额度；进入前看到预计收费项和上限。
- 空间租金与模型用量分开显示。长任务、视频生成和第三方订阅需要单独确认。
- 作者不能看到访客的密钥；进入空间不授权作者任意消耗额度。
- 先做用量记录、预算停止和失败不重复扣费，再提供平台 Token 包。仅在交易阶段增加订单和资金账本，不提前把生活空间改成经济模拟器。

### 两档授权（条款草案，发布前再确认）

一档面向个人使用、装修与符合约定的日常分享；另一档允许在收费空间和商业体验中使用。两档都单列“能否修改、能否分享改作、能否向访客交付原始文件”。商业使用不自动包含模型源文件再售卖权，付门票也不自动买下屋内积木。

出售对象可以是道具、动作、皮肤、VRM 装饰、空间模板和工具。许可记录伴随资产进入组合空间，缺少许可信息不作为可商业销售的默认素材。具体条款、权利确认和投诉处理由正式商业准备阶段审查，不在本计划中当作法律结论。

### 平台收入分开验证

1. 内容和空间索引、搜索与明确标注的推广服务。
2. 平台成交的积木包或租用订单按约分成，早期可让利；不对未提供成交服务的链接凭空收佣。
3. 工具、原材料服务、模型额度与订阅内容连接；是否存在转售或连接权限逐项确认。
4. 品牌植入、IP 体验和联名活动单独商业洽谈。

先不写死抽成、排名付费规则和订阅价格。上线付款前必须跑通费用告知、授权交付、失败取消、退款、争议记录与创作者结算。付费推广与自然排序明确区分。

验收：至少一位创作者和一位独立访客完成“发现 → 看清玩法与费用 → 租用 → 使用自带额度 → 离开并带回经历”的真实流程，并做一次失败退款演练。只有技术订单成功，不算经营验证成功。

## 十二、阶段 8：IP、游戏体验和更大的世界

魔法学院、恐怖主题建筑、梦幻影城和游乐园可以成为合作体验方向；具体 IP、角色、声音、音乐、品牌和游戏须取得对应授权后才能销售或推广。

先做一个可独立进入、可回到自家空间的小型合作体验，再扩展持续内容。二维动作游戏、附身操控、多 Agent 编排、多人同步、战斗规则和共享大型空间分别立项，根据体验需要加入，不能捆在第一版里。

平台竞争力作为待验证假设：可用素材、创作者经验、可迁移经历和真实访问关系能否持续积累。不能仅靠“别人复制客户端没有用”判断壁垒成立。

## 十四、执行和验收方式

- 只细化即将做的一个阶段，远期保持目标、依赖与放行条件。避免为还没用到的市场和多人功能提前写大框架。
- 每个小改动：失败测试 → 最小实现 → 回归 → 审查 → 独立提交。真实服务和画面体验另留验收结果。
- 将 Agent、空间物件、表现与声音按边界分配任务；同一文件明确负责人。构建保持串行，不同时开多个重型任务占用用户电脑。
- 不使用桌面自动化，不读取真实凭据做诊断，不执行付费生成或对外发布，除非用户明确授权对应动作。
- 记录每活跃小时模型／语音用量、后台调用次数、进入成功率、动作完成率、用户是否主动回来看它。先取得数据，再定商业指标与性能门槛。
- 下一步从阶段 1 的文字链路开始。完成“感知房间 → 去点唱机 → 操作 → 回报”的真实体验后，再接语音转写和更丰富的自主生活。
