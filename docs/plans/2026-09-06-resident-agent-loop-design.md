# 居民通用 Agent 循环设计

日期：2026-09-06。状态：设计已确认，第一批通用运行层进入实现与验证；当前验收和安装结果见本文末尾及证据记录。

本设计根据用户最新要求调整已有路线：先建立通用循环，再用点唱机验证。不能为听歌写一套固定问答，不能把工具失败直接当作整件事失败，也不能要求用户为每个操作补齐步骤。

## 1. 要解决的核心问题

居民需要在空间里持续拥有上下文、意图和行动能力。用户说话只是唤醒它的一种方式；没有用户输入时，它也能发现可做的事、形成自己的小目标、使用物件、根据结果改变安排。

“自主”不等于持续生成对白、频繁走动或无限调用模型。它可以安静做一件事，也可以等待。关键是行为来自对当前环境和经历的判断，执行结果会影响下一次选择。

设计目标：增加一个支持的物件后，提供该物件的状态、能力与执行器，居民就能尝试使用；不用再给主循环增加“咖啡问答”“电视问答”分支。

## 2. 一个循环，两种节奏

```text
用户消息／相关环境变化／行动结束／约定时间到达
                       ↓
          更新观察、当前意图、经历与可用能力
                       ↓
                    Agent 判断
             ┌─────────┼──────────┐
          查询工具    执行动作    交流、等待或结束意图
             │         │             │
             └──实际结果──→ 更新观察 ───┘
                           ↓
                有新依据就继续，无需思考就休眠
```

应用负责跨事件的唤醒、保存、打断和工具执行。选中的模型后端负责一轮内的推理与多次工具调用。已有 Codex 会话能在同一轮反复调用工具，应复用；不在外面再套一个不断催促“继续”的模型循环。

人物行走、动画、播放进度仍由本地执行器推进。一次行走开始后，应用等待它的结果，不逐帧让模型决定下一步脚往哪放。

两种节奏使用同一名居民、同一组能力和同一份经历：

- 用户参与时，模型理解交谈、接续目标、调用工具，必要时自然提问。
- 用户不参与时，模型根据环境、性格提示、近期活动和已有安排选择事情做；无需把每次决定说给用户听。

## 3. 决策归属

| Agent 决定 | 应用负责 |
| --- | --- |
| 做什么、为何做、是否还值得继续 | 当前真实状态、可用工具和实际执行 |
| 缺什么信息，自己查还是询问 | 查询范围、权限、调用成本和结果格式 |
| 如何比较候选，是否换办法 | 确认对象存在，执行导航、设备和播放操作 |
| 一次失败后继续、换方案还是等条件变化 | 去重、取消、过期结果隔离、预算和唤醒 |
| 何时交流，哪些经历值得记住 | 文字、TTS、动作表现及可追溯记录 |

应用可以有通用的运行状态，如执行中、等待事件、等待用户、已结束；不能有 `等待用户回答音乐类型` 这类业务专用状态。用户下一句由模型理解，不依赖关键词或按钮编号来切换流程。

## 4. 每次思考需要知道什么

上下文按需提供，避免把完整房间、所有歌单和全部历史塞进每一轮：

1. **自身与当前环境**：所在空间、位置、当前活动、可见物件及其状态；未知数据明确为未知。
2. **当前意图**：用户正在委托什么、居民原来在做什么、尚待解决的问题；目标来源保留为用户委托或自主安排。
3. **近期事实**：真正完成的动作、失败原因、用户的明确选择、刚发生的重要变化。
4. **偏好与经历**：用户明确表达的偏好、居民的性格提示和过去体验。临时偏好与长期偏好分开；一次“今天听爵士”不写成永远喜欢爵士。
5. **当前能力**：哪些设备可用、哪些工具已经接通、所需权限与成本。只宣告真实可执行的能力。
6. **互动条件**：是否允许自主活动、当前是否宜打扰、可用预算及休眠条件。

模型的推测与事实分开保存。日志记录行动摘要和依据事件，不保存隐藏思考过程，不让“想做”“准备做”变成“已经做过”。

空间描述、歌单名、内容标题都是数据，不能变成系统指令。凭据、下载地址、任意本地文件和其他房间的私密资料不进入环境上下文。

## 5. 能力如何接入

采用一个小型能力登记表，统一产生模型工具描述、调用校验和界面可用状态。避免在会话、传输和提示词里分别维护互相不一致的工具名单。

能力分为几类，以下是职责而非本轮全部新增工具：

- **观察**：查看空间、物件、正在执行的操作、相关状态变化。
- **发现与读取资源**：列出已有内容、搜索、分页读取详情；音乐只是其中一个领域。
- **身体与物件操作**：移动、开始或停止活动、准备资源、使用设备。具体执行仍由现有引擎和服务完成。
- **交流**：输出自然语言，按用户配置用文字或 TTS 表达；询问没有固定台词。
- **意图与经历**：保存当前安排、可恢复的进展和有依据的经历；结束或暂存意图。
- **等待**：登记相关事件或下次合适的唤醒时间，然后释放模型调用。

工具应当够小，允许组合，同时保留有实际意义的动作，例如“使用点唱机”可以包含走到操作点和按下播放；选哪张歌单、为何选择、失败后怎么办不放进这个动作里。

不使用一个可执行任意命令的万能工具。创作者声明的能力只能绑定到应用已支持的执行器；上传一个 GLB 不会自动获得联网、付款或本地文件访问能力。

每个物件提供：稳定编号、简要说明、当前状态、交互位置、可发现的能力以及当前不可用原因。核心循环不检查“这个对象是不是咖啡机”；对象与执行器负责具体交互条件。

## 6. 工具返回事实，循环决定后续

通用返回至少包含：

- 本次操作编号与状态：完成、执行中、失败、取消。
- 已产生的实际效果及相关状态版本。
- 失败时的原因代码和可观察事实，无法确认的结果标为未知。
- 长操作的查询或取消标识；必要的后续状态查询能力。

工具失败不自动结束模型回合。模型可以查询更多信息、调整参数、选择另一个可用对象、延后安排，或者在确实需要时向用户说明。

执行中也不等于成功。模型明确结束某个意图时，需要引用能够支持结果的操作或观察；提供方的“一轮回复结束”只表示本轮停止输出，不能直接把尚未完成的目标标记为完成。等待用户、等待事件、完成、取消与无法继续需要分别记录。

长动作可以返回操作编号并让循环等待完成事件。现有短时异步调用可以继续直接等待结果，首期不把所有动作都重写成任务系统。

允许安静结束一轮思考：已经执行有效操作或登记等待条件时，可以不产生对用户的对白。使用明确的结构化结束信息区分正常静默、等待和提供方异常；不能因为没有文字就报错，也不能把所有空回复都当作成功。

本轮工具调用权限与已提交活动的生命周期分开。轮次结束关闭调用入口，跨轮次的操作和等待由居民运行层持有；只有明确取消、替换、失效或达到运行边界才终止相应操作。取消当前委托也不能误停用户手动启动的活动。

## 7. 遇到问题怎样自己处理

给模型判断原则，不规定“失败必须依次做 A、B、C”：

- 信息可以通过现有工具查到时，主动查询，不把内部准备工作交给用户。
- 存在符合原意的替代方案时，结合上下文尝试；不擅自改变用户指定的关键目标。
- 用户给过足够依据就直接行动；没有依据且选择差异重要时才询问。
- 用户委托与自主消遣区别处理。用户点名要听某首歌，不能换成跳舞后声称完成；居民自己想听歌而暂时播不了，可以保留失败经历并换件事做。
- 没有新依据时不重复相同失败调用。暂时条件不具备可以等待状态变化；达到预算或重试边界就休眠或准确说明进展，不宣布成功。
- 播放等有副作用操作超时后先查真实状态，结果未知时不能盲目再执行，避免重复播放或覆盖手动操作。
- 登录失效、授权不足、付费与不可逆操作等确实需要用户参与的事项才升级处理；不自动打开授权弹窗。

询问应当说明已经知道什么，以及尚缺哪个有意义的选择。不能把每次工具错误原文直接作为最终聊天答复，也不能靠隐瞒失败维持“很聪明”的假象。

## 8. 用户不说话时，它怎么生活

首期不做饥饿、心情等游戏数值，也不增加多个决策 Agent。

一次自主唤醒给它当前环境、正在做的事、近期经历、性格提示和自主活动范围。它可以继续原活动、尝试某个物件、选择新活动、留下少量有意义的记录，或者决定暂时无事可做。选择活动的内容来自模型判断；本地规则只负责动作推进、重复抑制和运行节奏。

唤醒来源是活动完成、相关物件变化、用户回来、已有安排到时，以及空闲后的低频检查。应用合并重复事件，忽略无关的逐帧变化。模型可以提出下次唤醒时间，应用按配置的最低间隔和预算执行，避免零延迟自我唤醒。

用户明确操作或发出新指令优先。一个居民只保留一个会改变世界的执行序列；自主思考不能抢走用户刚选的歌、覆盖手动动作或制造并发设备命令。聊天是否需要停止当前活动由上下文和资源冲突判断，普通交谈不必让人物原地停住。

问了用户一句话，不代表整个世界停住。挂起的委托保留，允许不冲突的日常活动继续；不反复提醒用户回答。用户回复后，模型结合之前的问题、当前状态和新话语重新判断，允许改口或换话题。

后台默认少说话，显著变化与用户相关结果再展示。用户可以统一暂停自主活动、调整主动交流频率和用量上限。

应用退出后没有持续运行的服务器，就停止思考。重开时恢复已保存意图与事实，重新观察状态；只补算已有规则支持的时间变化，不编造离线经历。

## 9. 连续性和成本的最小实现

先保存一份居民运行记录：居民身份、当前空间、未结束的意图、正在执行的操作编号、等待条件、近期结果、必要的偏好和会话定位。使用现有本地保存方式，不引入分布式调度或新的向量数据库。

模型供应商的会话编号与居民身份分离。切换模型时，应用用有限的结构化摘要重建上下文，不能只依赖某个 CLI 的聊天历史。断线恢复先核对世界和设备状态，再决定哪些动作可续接，不能重放所有历史命令。

用量按一次唤醒和一段自主运行分别限制。空闲、等待动作、等待用户时都不持续推理；固定动画和播放不消耗模型调用。预算用尽表示暂停自主思考，已有安全活动可继续，用户能看见原因。具体默认额度通过真实测试再定。

时长、工具调用次数和自主唤醒频率由应用实际限制，不能只写进提示词。提供方能返回用量时累计实际用量，不能返回时明确显示可观测范围，不伪造精确费用。一个原生模型回合停不下来时，应用有权中断并保存已知结果。

## 10. 当前工程差距与复用点

当前代码已经具备一轮内的工具循环，主要缺少跨事件的生活循环、更多可发现能力和可恢复意图：

- `ResidentCodexAgent` 已处理多次工具请求与回传；不需要自建替代 Codex 推理循环。
- `AgentConversationService` 已有按空间区分的会话和动态世界资料，后续需要纳入意图、事件和能力版本。其他后端是否支持同等工具循环仍须逐项验证。
- `ResidentWorldToolSession` 已处理调用去重、取消和世界归属，目前只开放四个世界工具；未来从登记表生成本轮能力范围。
- 当前消息入口在结束时取消本轮工具租约，新增跨轮次操作需要交由居民运行层持有。现有成功音乐操作已经释放临时归属，正常消息结束不会暂停该成功播放，不需要为新设计破坏这项行为。
- `ResidentCodexAgent` 当前将正常结束但无最终文本视为 `noFinalAnswer`；自主静默轮需要明确的结束合同，不能强迫居民每次开口。
- `WorldAgentContext` 与现有活动执行器继续维护真实位置、活动和运行结果。
- `ResidentActivityOutcome` 已确认到达与实际播放，错误反馈仍过于单一。当前截图对应路径没有可查歌单的工具，因此模型无法自行继续。
- 启动 `restoreSavedProgramPresentation()` 只恢复展示；`restoreSavedProgramPlayback()` 未被调用。显示有历史歌单与当前可直接播放是两个状态，必须让模型区分。
- 已有本地同步歌单库、歌单分页服务和曲目准备队列，可以提供资源工具；UI 的异步点击回调不能直接当作完成结果。

Codex 动态工具目前在新建会话时注册。工具集合升级时需要明确能力版本及会话重建策略，避免恢复旧会话后仍看不到新增工具；居民经历应当保留。

## 11. 点唱机只作为第一个验证场景

补充可复用的音乐能力：读真实播放状态、列出已有歌单、读取歌单内容、准备明确选中的曲目。沿用实际活动与播放执行器，不增加“询问音乐类型”专用工具，不把自然语言匹配塞进播放器。

例如“随便放点适合现在的”与“我想听爵士”和“去听歌”的选择依据不同；模型可以查询、比较、直接选择或追问，不能要求所有请求都走相同顺序。工具返回空列表、未加载完整、当前来源不支持、网络失败、未授权等不同事实，模型据此继续判断。

首期音乐查询以用户已有歌单为范围。只把真实数据提供给模型，不编造歌单和歌曲。当前 Apple Music 外部播放来源尚无等价的居民状态验证与取消支持，须如实标为不支持，不能用本地播放状态代替验证。

同一循环随后用另一个实际已支持的活动验证迁移。电视、咖啡机可用于合同设计示例，但实现和资产尚未就绪时不宣称可玩。

## 12. 实施顺序与验收

1. **通用运行层**：统一事件入口、意图生命周期、等待与打断、能力登记、结果回传；先复用当前模型与世界执行器。
2. **用听歌验证主动交互**：提供已有歌单工具，测试多种自然表达、无需追问的请求、确需追问的请求、失败后的恢复和用户改口。
3. **用现有活动验证自主性**：活动结束或低频唤醒时让模型自行安排，观察不打扰用户的连续生活；不先新增大量物件。
4. **补保存与恢复**：重开、切换空间、模型断线后恢复意图，核对实际效果，不重复操作。
5. **再扩展物件和模型提供方**：新能力通过登记和执行器接入，验收不要求主循环新增业务分支。

保存与恢复放行前，前面增量只承诺应用运行期间的连续性；不能把模型服务保留了一段聊天历史等同于已经实现居民存档。

验收检查行为与事实，不要求固定提问台词或固定工具顺序：

- 能自己查询的问题，不反问用户；已有偏好不反复询问。
- 一次工具失败后，有依据地继续、换方案或等待；没有依据时不无限重试。
- 查到候选后能使用其真实编号操作；没有候选不捏造。
- 用户改口、停止、手动切歌和切换空间后，旧操作不继续产生效果。
- 模型说完成时有实际结果支持；模型本轮结束不丢失尚待解决的意图。
- 用户不输入时能安排已支持的活动；一项自主活动失败不让整个居民停止生活。
- 安静观察期间有合理行为，也有不调用模型的等待时间；不把高调用次数当作活跃度。
- 添加第二种能力时，核心循环不新增专用问答状态。

验证分两层：确定性测试覆盖生命周期、去重、取消、等待和结果；真实模型用多种表述与故障场景观察工具轨迹、追问必要性和行动结果。两类证据分别记录，测试替身不能代替真实出声或画面验收。

## 13. 设计阶段交付边界

本轮只交付通用设计与路线调整。点唱机的局部自动选歌尝试已经撤回，没有将其作为最终方案，也没有安装只改错误提示的新包。后续实现以本设计为依据，不沿用“工具失败就让用户手动处理”或“固定提问后执行”的路径。

已完成独立只读审查，核对当前会话、工具名单、歌单服务与播放接线。审查补充的静默回合、消息租约与长操作分离、应用强制预算已纳入设计。没有以此宣称通用循环已经实现或通过运行验收。

## 14. 第一批实现范围

用户确认后，先接通应用运行期间的单居民循环：统一接收文字、语音转写、活动变化和低频唤醒；通过当前 Codex 会话持续调用正式世界工具，增加读取居民状态与更新意图两个通用工具。不添加音乐类型专用状态或固定问答。

- 工作期间的新消息优先送入当前模型回合；不能送入时按原顺序排到下一轮。交付不确定的消息单独提示，不擅自重发。
- 明确停止立即取消思考、朗读及仍归属于居民的活动；普通回合结束保留已接受的活动。手动接管与切换空间清理旧任务，迟到回调不修改新任务。
